# In-app updates

The update controller is shared across screens for the JS session. The Settings Updates row provides manual checks and an explicit restart action. Its trailing icon shows check, current, restart-ready, or retry status; a spinner shows ongoing work. Tapping the ready icon asks for confirmation and warns about unsaved entries. There is no separate update screen or global notice. Automatic checks and downloads never navigate, show alerts, or reload.

Startup and foreground transitions trigger quiet checks, with a 30-minute session cooldown measured from attempts (including failures) and Expo’s native last-check timestamp. Manual checks bypass the cooldown. The controller defers to native startup/check/download activity and observes cached pending updates through `useUpdates()`. When startup finishes, it coordinates another check only if the cooldown permits. Native startup configuration is unchanged.

SDK 57 `downloadProgress` drives a mint determinate ring and the accessibility/tooltip percentage during downloads. Unknown download progress falls back to a spinner; checks and restarts also use a spinner. The remaining states retain the existing sync, checkmark-circle, restart, and error-circle icons. The ring uses React Native views and requires no new native module or runtime change. A download or reload error can be retried; automatic failures stay quiet. The controller serializes its operations and blocks additional calls while native startup work is active. Web, development and Expo Go do not call update APIs.

This change uses existing native modules only and is suitable for an OTA to a compatible installed release runtime. No runtime, channel, native configuration, or publish operation is part of this implementation. A real release-build check/download/restart still needs validation against an intentionally published compatible update.

Reference: https://docs.expo.dev/versions/v57.0.0/sdk/updates/

## Decision: Settings visit feedback (2026-11-06)

Each visit to Settings starts the Updates row with the default check icon instead of the previous visit's success or failure. This is presentation state only: the shared controller, automatic-check cooldown, and downloaded update remain intact. In-progress checks/downloads/restarts and a downloaded update waiting for restart still show their live state. A manual check shows its result for the current visit; old error alerts are not replayed on re-entry.

Hovering the status icon, focusing the row with the keyboard, or holding it on touch reveals a small floating status tooltip above the icon. The tooltip overlays nearby content without changing the row height or moving other settings. It explains the current icon or spinner, including download percentage when available. Hover/focus/hold never starts a check or restart. Leaving and revisiting Settings clears the tooltip. Restart still requires explicit confirmation.

## Decision: running release identity (2026-11-05)

Settings ends with a tappable version/release line, separate from the unchanged compact Updates row. The details use the session's `expo-updates` constants (`updateId`, `createdAt`, `runtimeVersion`, `channel`, `isEmbeddedLaunch`, and emergency-launch diagnostics), never the downloaded/pending update from `useUpdates()`. Embedded launches, including emergency fallback, therefore describe the embedded JavaScript actually running. Development/Expo Go, web and disabled updates have explicit labels. Unknown commit metadata stays unknown; unstamped OTA launches use the running update ID as a fallback. Version comes from SDK 57 `Constants.expoConfig.version`, which describes the running manifest, rather than assuming the installed native binary version identifies its JavaScript.

CI runs `scripts/stamp-release.mjs` immediately before `eas update` exports/publishes. It replaces the checked-in null value in `src/generated/release.ts` with the full verified `GITHUB_SHA`. The script requires GitHub Actions, matching HEAD, and a clean checkout including untracked files, so ordinary local edits are never automatically attributed to HEAD. The generated source travels with each bundle and survives EAS environment loading; it is not a local environment variable or mutable server-side release label. No Git lookup occurs in the app. Local builds remain unstamped. Do not commit the CI-generated value or reuse a stamped checkout for another export.

EAS CLI 27.4.1 retains `--environment production`. Expo's environment documentation says that with this flag only the selected EAS environment is used for update variables; a shell `EXPO_PUBLIC_*` assignment alone is insufficient. Generating source avoids this precedence issue without changing remote environment state or native/runtime configuration.

There is no installed `expo-clipboard` dependency. Inspection of the installed React Native 0.86 source confirms native Clipboard implementations in Android's `ClipboardModule.kt` and iOS's `RCTClipboard.mm`, with a `setString` method, although the JS Clipboard export is deprecated. Copy details uses the public `TurboModuleRegistry.get('Clipboard')` capability lookup and this existing native method, without adding a module or assuming transitive support. If absent, on web, or if copying throws, it reveals instructions to touch and hold the complete selectable details and use the system Select all / Copy menu (or browser selection). Only a successful native call reports “Details copied.” The sheet reuses the existing platform-native AppSheet and shared form controls. Real Android/iOS clipboard/selection menus and release fallback launches require device validation; renderer tests verify direct copying, missing/failed capability fallback, opening and dismissal.
